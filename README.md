# STRIKE ZONE · Stadium Live — POC v7

## 실행

압축을 해제한 후 `dist/index.html`을 브라우저에서 열면 가상 크레딧으로 플레이할 수 있습니다. Node.js가 있다면 프로젝트 폴더에서 `node server.cjs` 실행 후 http://127.0.0.1:4173/ 에 접속할 수도 있습니다.

화면은 1080×1920 세로 구도를 기준으로 구성했습니다. 540×960 CSS px 화면을 2배 해상도로 출력하면 1080×1920입니다.

## v7: 배트만 보이는 상승 스윙

- 손과 팔의 메시·관절 계산을 제거하고 3D 배트만 표시합니다. 손 자산 스크립트를 로딩하지 않습니다.
- 접촉 직전부터 배트가 위로 향하고, 공을 통과한 뒤 높은 위치로 이어지는 상승 궤적을 적용했습니다. 접촉 구간은 화면 기준 약 18도 상승하도록 조정했습니다. 이 각도는 POC의 시각적 조정값입니다.
- 타격 전후 회전 속도의 연결을 맞추고, 마무리에서 배트가 다시 내려오던 곡선을 제거했습니다.
- 헛스윙은 처음부터 공 아래의 코스를 따라 같은 상승 동작을 합니다. 접촉 직전에 갑자기 배트를 아래로 빼는 움직임을 제거했습니다.
- 투수 쪽으로 치는 앞뒤 방향, 기존 좌우 스윙 흐름, 배트 길이, 공 접촉 시점과 배당·정산 엔진을 유지했습니다.

참고 영상: [MLB — Best of Catcher Cam at MLB Summer Camps (Part 2!)](https://www.youtube.com/watch?v=wM_k9_4Fmmg). 브라우저에서 실제 영상을 재생하고 약 14~15초 구간의 준비·스윙·높은 마무리 자세를 확인했습니다. 포수 시점의 상승 마무리를 참고해 게임의 기존 타격 방향에 맞게 구성했습니다. 영상 프레임이나 선수 이미지는 게임에 포함하지 않았습니다.

- 상단 투수·배당, 하단 조작 영역의 전후 화면 비교 통과.
- 실제 HIT/OUT, 상금 확정, 자동 정산, 입력 잠금, 짧은 연출 및 모션 줄이기 검증 통과.
- 소프트웨어 대체 렌더링과 파일 직접 열기 방식의 오프라인 실행 확인.

v6의 손 원본과 변형 도구는 이전 작업 보관용으로 남겨두었습니다. v7 게임에서는 사용하지 않습니다.

## v6: 손잡이를 감싸는 양손과 자연스러운 팔 연결

- 둥근 장갑 도형을 좌우 손가락 형태가 있는 3D 손 메시로 교체했습니다. 네 손가락은 손잡이 둘레로 감고 엄지는 검지 쪽으로 접어 그립을 만들었습니다.
- 접촉 순간 아래 손은 손바닥이 아래를, 위 손은 손바닥이 위를 향하도록 자세를 조정했습니다. 양손의 회전을 따로 제어하고 타격 후 팔이 돌아가도록 연결했습니다.
- 손목과 장갑 끝을 연결하고, 길이가 고정된 위팔·아래팔과 굽혀지는 팔꿈치를 적용했습니다. 팔을 길게 늘려 손 위치에 맞추던 형태를 개선했습니다.
- 손잡이 방향을 따라 안정적인 회전 기준을 사용해 손목이 갑자기 뒤집히는 현상을 줄였습니다. 타격 후 손을 왼쪽으로 급하게 당기던 움직임도 완화했습니다.
- 배트 몸통과 손잡이를 더 날렵하게 다듬고 손잡이 끝을 막아, 마무리 자세에서 검은 구멍처럼 보이던 부분을 수정했습니다.
- v5.1에서 수정한 투수 방향 타격, 공과 배트의 접촉 시점, 얇은 타격존과 배당·정산 엔진은 유지했습니다.

### v6 검증

- 세 화면 크기 × 25칸 × HIT/헛스윙, 150개 접촉 사례와 상·하단 UI 가림 검사 통과.
- 25칸 × HIT/헛스윙 × 기본/짧은 연출, 100개 사례에서 투수 방향으로 통과하는 기존 타격 궤적 확인.
- 실제 HIT/OUT, 상금 확정, 자동 정산, 중복 입력 차단, 짧은 연출 및 모션 줄이기 검증 통과.
- WebGL 대체 렌더링과 파일 직접 열기 방식의 오프라인 실행 확인.

손 모델은 MIT 라이선스의 WebXR Input Profiles Assets 1.0.20을 그립 자세로 변형했습니다. 원본은 source-assets/hands, 변형 도구는 tools/bake-batting-hands.cjs에 포함했습니다. Node.js가 있으면 프로젝트 폴더에서 node tools/bake-batting-hands.cjs로 손 메시를 다시 생성할 수 있습니다. 이는 관절 계산을 적용한 POC 연출이며 선수 모션 캡처는 아닙니다. 출처와 라이선스는 THIRD-PARTY.md에 있습니다.

## v5: 양손으로 잡은 3D 배트와 코스별 스윙

1. **손과 팔 연결**: 장갑 낀 두 손, 손목과 짧은 팔을 연결했습니다. 코스별 준비 위치를 먼저 잡고 손잡이는 작은 궤도로 움직입니다.
2. **고정된 입체 배트**: 기존 평면 이미지를 회전시키던 방식에서, 원통형 단면·테이퍼·손잡이·끝면을 갖춘 실제 3D 메시로 교체했습니다. 배트 길이와 두께는 모델 안에서 고정되며 방향과 조명에 따라 입체적으로 보입니다.
3. **임팩트 중심 속도**: 화면에서 배트가 이동하는 거리를 기준으로 시간을 배분해 타격 직전 가속하고 이후 감속합니다. 공과 배트는 같은 시간 기준으로 움직입니다.
4. **높이별 세 가지 스윙**: 1~2행은 높은 공, 3행은 가운데 공, 4~5행은 낮은 공의 준비 각도와 마무리 궤적을 사용합니다. 투수·배당·하단 조작 영역을 침범하지 않도록 궤적과 표시 범위를 제한했습니다.

새 장면은 직접 구성한 POC 3D 모델입니다. 실제 선수의 모션 캡처나 해부학적 인체 시뮬레이션은 아닙니다. 25칸 선택과 위험 코스 배치, 배당 및 정산 엔진은 그대로 유지했습니다.

### v5 확인한 내용

- 3개 화면 크기 × 25개 칸 × HIT/헛스윙, 총 150개 3D 접촉 사례 확인.
- 배트의 실제 길이 고정과 공 도착 좌표 일치 확인.
- 준비에서 임팩트까지 손잡이의 최대 이동 거리는 화면 너비의 약 5.1%.
- 검사한 HIT 궤적의 최대 속도 시점은 임팩트에서 1ms 이내. 이는 애니메이션 곡선 검사이며 기기별 표시 지연을 뜻하지 않습니다.
- 상단 투수·배당 및 하단 버튼 영역의 전후 화면 비교 확인.
- 테스트 환경의 1080×1920 재생에서 프레임 간격 중앙값 약 16.7ms, 최대 약 33.3ms. 실제 기기 성능은 다를 수 있습니다.
- 기존 HIT/OUT, 캐시아웃, 전체 안전 칸 자동 정산, 입력 잠금, 짧은 연출, 모션 줄이기 및 네 가지 화면 크기 검증 통과.
- WebGL을 사용할 수 없을 때 같은 입체 모델을 소프트웨어로 그리는 대체 경로와 실제 HIT 확인.
- 압축 해제 후 파일을 직접 여는 오프라인 실행 확인. 플레이 중 외부 라이브러리 서버에 접속하지 않습니다.

### 사용 라이브러리

Three.js 0.180.0을 데모에 포함했습니다. MIT 라이선스 전문은 dist/vendor/THREE-LICENSE.txt, 출처는 THIRD-PARTY.md에 있습니다. GPU가 지원되면 WebGL 2를 사용하며, 지원되지 않으면 소프트웨어 렌더링을 사용합니다. 소프트웨어 방식은 기기에 따라 프레임 속도가 낮아질 수 있습니다.

## v4: 야구 스윙 동작 개선

- 같은 타석 위치에서 배트를 뒤로 당기는 준비 동작을 시작합니다.
- 손잡이가 먼저 이동하고 배트 몸통이 뒤따라 가속하도록 곡선을 적용했습니다.
- 배트를 깊이 방향으로 회전시켜 원근에 따라 보이는 길이와 각도가 달라집니다.
- 공을 가로질러 맞힌 뒤 뻗어 나가고, 위쪽으로 감기며 화면 밖으로 마무리합니다.
- 공·배트·짧은 잔상을 같은 시간 기준에 맞췄습니다. 임팩트 때 애니메이션을 강제로 멈추거나 접촉 자세로 되감지 않습니다.
- 일반 연출 약 0.92초, 짧은 연출 약 0.47초. 모션 줄이기 설정은 유지합니다.

실사 배트 이미지에 투영과 보간을 적용한 POC 연출입니다. 실제 선수의 모션 캡처나 인체 관절 시뮬레이션은 아닙니다. 배당·결과·확률 엔진은 변경하지 않았습니다.

동작 참고: [MLB Statcast — Attack Angle](https://www.mlb.com/glossary/statcast/attack-angle). 준비 위치에서 내려온 배트가 접촉 후 위로 이어지는 스윙 흐름을 참고했습니다.

### v4 검증

- 세 화면 크기 × 25개 칸 × HIT/헛스윙, 총 150개 화면상의 접촉 좌표 확인.
- 준비 자세의 위치, 궤적의 연속성, 공·배트·잔상의 시간 동기화와 연출 종료 후 정리 확인.
- 실제 클릭으로 HIT·OUT·캐시아웃·자동 정산·중복 입력 차단·짧은 연출·모션 줄이기 및 네 화면 크기 확인.

## v3에 적용한 세 가지

1. **배경과 투수의 공간 통일**: 인물이 없는 새 야간 경기장 배경을 사용하고 마운드와 투수의 발 위치를 맞췄습니다. 투수의 밝기·색감·발밑 그림자를 조정했습니다. 기존 정지 투수를 가리던 사진 패치는 제거했습니다.
2. **손에서 출발하는 투구와 배트 접촉**: 릴리스 자세의 실제 손 위치를 기준으로 공이 출발합니다. 선택한 칸에서 공과 배트의 몸통이 만나도록 회전 중심과 접촉 지점을 계산합니다. HIT는 타구로 이어지고 OUT은 공 아래로 헛스윙합니다. 네 자세 사이에 짧은 전환을 추가했습니다.
3. **얇고 투명한 타격존**: 보드와 셀의 배경을 투명하게 낮추고 테두리를 얇게 조정했습니다. 경기장 시야를 확보하면서 선택한 칸과 HIT/OUT 결과는 구분합니다.

투수 좌우의 배경 없는 현재 배당/다음 성공 배당 UI를 유지했습니다. 투구와 배트 동작은 결과를 표현하는 연출이며 타이밍 조작으로 확률이나 배당이 바뀌지 않습니다.

## 유지한 기능

- 플레이 중 하단에서 지금 확정할 금액, 다음 성공 시 지급액, 다음 1회 성공 확률을 비교합니다. 지급액은 원금을 포함하며 내부 배당으로 정산합니다.
- 캐시아웃·OUT·전체 안전 칸 성공 시 전광판 스타일 결과 화면이 열립니다. 안타 수, 확정 배당, 베팅, 총 지급액, 순손익, 현재 크레딧을 보여줍니다.
- 결과에서 보드 확인 또는 다음 라운드 준비를 선택할 수 있습니다. 다음 라운드 준비만으로 베팅하지 않습니다.
- `?` 도움말에서 기본/짧은 연출을 고를 수 있고 운영체제의 모션 줄이기 설정을 존중합니다. 소리는 상단 음표 버튼으로 켭니다.

## 게임 규칙

- 시작 크레딧 1,000 CR, 기본 베팅 100 CR, 위험 코스 3개.
- 베팅은 1~1,000 CR, 최대 소수 둘째 자리. 위험 코스 1~24개.
- 25칸에 위험 코스를 균등 배치하며 라운드 동안 고정합니다.
- 실패 1회로 종료. 1회 이상 HIT 후 캐시아웃 가능.
- 모든 안전 칸 성공 시 자동 정산.
- 투구 연출 중 베팅·코스 선택·캐시아웃·크레딧 초기화를 잠가 중복 처리를 막습니다.
- 실제 돈, 입출금, 로그인, 영구 저장 기능은 없습니다. 새로고침 시 진행 상태와 크레딧이 초기화됩니다.

## 배당

P(k) = C(25-M,k)/C(25,k)
X(k) = 0.99/P(k), k >= 1

기존 조합 정수/BigInt 엔진을 유지했습니다. 배당은 소수 둘째 자리 반올림으로 표시하고, 지급액은 내부 배당으로 계산 후 0.01 CR 미만을 절사합니다. 정산 단위 적용 후 기대 반환율은 이상적인 99%보다 소폭 낮아질 수 있습니다. Stake의 지급 상한·반올림·세부 운영 규칙까지 동일하게 검증한 상용 제품은 아닙니다.

예: 100 CR, 위험 3개, HIT 2회 → 지금 128.57 CR / 다음 성공 시 147.85 CR / 다음 성공 확률 86.96%.

브라우저 crypto, rejection sampling, Fisher–Yates로 배치합니다. 서버 권한 검증과 시드 공개 기반의 공정성 검증은 구현하지 않았습니다.

## 확인한 내용

- 위험 코스/성공 횟수 300개 조합에서 이상적인 확률 × 배당 = 0.99.
- 현재/다음 지급액과 성공 확률, HIT/OUT 및 결과 전광판 금액.
- 투구 중 중복 입력과 중복 지급 차단, 전체 안전 칸 자동 정산.
- 다음 라운드 준비 시 크레딧 차감 없음.
- 기본/짧은 연출, 모션 줄이기, 540×960·390×844·360×640·1280×900 화면.
- 3개 화면 크기 × 25개 칸, 총 75개 접촉 좌표 검사: 배트 접촉점과 공 도착점의 계산 오차 0.001 CSS px 미만.
- 실제 투구 출발점과 손 기준점 일치, OUT 시 헛스윙 간격, 투명 보드 및 새 배경 적용 확인.
- 릴리스·접촉 장면 캡처를 통한 시각 확인. 좌표 검사는 자산의 접촉 기준점에 대한 검사이며 물리 시뮬레이션은 아닙니다.
- WebMCP의 읽기/시작/선택/캐시아웃 도구를 테스트 레지스트리에서 검증. 해당 브라우저의 네이티브 WebMCP 미지원으로 실제 네이티브 연결 검증은 하지 못했습니다.
